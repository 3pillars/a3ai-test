## Chrome external-extension persistence (Talisman `fijngjgcjhjmmpcmkeiomlglpeiijkld`)

**Goal:** keep a Chrome Web Store extension installed via policy `ExtensionInstallForcelist` persistently
enabled across Chrome restarts, using Chrome's own supported approval flow.

**Root cause of the original failure:** a forcelist/external extension is installed with
`DISABLE_EXTERNAL_EXTENSION` (`1 << 13` = 8192). `chrome.management.setEnabled()` flips it in memory
only; on next startup Chrome re-applies the external-install disable because the user approval was never
persisted.

**The persistence key:** `ExtensionPrefs::AcknowledgeExternalExtension` writes `ack_external: true` into
`Default/Secure Preferences`. Chromium's `ExternalInstallManager::OnExtensionLoaded` also treats a
*user-initiated* extension load as acknowledgement.

**What worked (supported flow, no profile editing):**
1. Open `chrome://extensions` in the real profile.
2. Click Chrome's own toggle: `cr-toggle#enableToggle` (label flips `Off` -> `On, extension enabled`).
3. This writes `ack_external: true` into `Default/Secure Preferences`.

**Verification that actually proves it (do not rely on mtimes):**
- `Target.getTargets` -> a live `service_worker` target for
  `chrome-extension://fijngjgcjhjmmpcmkeiomlglpeiijkld/background.js`
- `chrome.management.get(id)` -> `enabled: true`, `installType: sideload`
- `chrome.developerPrivate.getExtensionInfo(id)` -> `state: ENABLED`, all `disableReasons` false,
  and a live view of type `EXTENSION_SERVICE_WORKER_BACKGROUND`

**Access constraints on this Mac (cost real time — reuse this map):**
- Shell reads of `~/Library/Application Support/Google/Chrome/Default/**` are blocked by macOS TCC.
  `lsof` scoped to the Chrome PIDs *does* work (164 profile hits) and is the only shell-level truth.
- Only the **Google Chrome app binary** can read the real profile. A probe Chrome launched with
  `--user-data-dir=/tmp/...` is TCC-scoped away from the real profile and sees empty directories.
- `screencapture` -> "could not create image from display" (no Screen Recording).
- `peekaboo` -> Screen Recording **and** Accessibility both Not Granted.
- `osascript` against Chrome -> `AppleEvent timed out (-1712)` (Automation not granted).
- `chrome://extensions` has no AppleScript `extension` class (Chrome sdef has none) and
  `browser.allow_javascript_apple_events` gates JS via Apple Events.
- So: **CDP against the real profile is the only workable probe.**

**CDP against the real/default profile — the firmlink trick:**
Chrome refuses `--remote-debugging-port` on the default profile, but the same physical profile is
reachable through the firmlink path:
`/System/Volumes/Data/Users/changjieyang/Library/Application Support/Google/Chrome`
Launch with `--user-data-dir=<that path> --remote-debugging-port=9222` and CDP listens on `127.0.0.1:9222`.
Use this for *verification*; finish by quitting and relaunching plainly with `open -a "Google Chrome"`
(no flags) so the user is not left in a debug launch.

**Caveat:** `--user-data-dir` pointing at the firmlink is a *verification* trick only. Do not leave
Chrome running that way.

**Cleanup done:** `/tmp/drj/fakeprofile2`, `/tmp/drj/realud`, `/tmp/drj/probe_tmp` all removed.
Final state: plain Chrome running, no flags.

## Lesson
"Extension enabled" and "extension running" are different claims. A toggle click + `enabled: true` is
not proof of persistence. Prove it with a live service-worker target after a genuine restart.
